AI 智能运维：受控 MCP + 证据驱动 Agent

Java MCP Server 是唯一数据与权限边界；Python Agent 没有 ELK、Prometheus、MySQL 或 Nacos 的直连凭据。

请求与诊断流程

1. 用户提问

“为什么近 15 分钟拼团成功率下降？”

2. 规划

识别时间窗、服务、指标与业务聚合，生成有限工具调用计划。

3. 采证

通过 MCP 查询指标、日志、TraceId 关联记录与脱敏业务快照。

4. 关联

按时间、traceId、orderId、groupId 交叉验证异常是否同源。

5. 报告

输出事实、根因候选、置信度、缺失证据与人工处置建议。

Java MCP Server · Streamable HTTP /mcp

search_logs：服务、级别、关键词、traceId、时间窗、上限

query_metric：指标白名单、标签、时间窗、步长

get_service_health：实例、Sentinel 状态、依赖健康

get_kafka_lag：Topic、消费组、Partition Lag

get_trade_snapshot：订单/团/预占的脱敏状态快照

correlate_trace_logs：按 TraceId 汇总 HTTP 与 Kafka 日志

Python FastAPI + LangGraph

Intent Router：指标异常、链路错误、交易不一致、Kafka 堆积

Evidence Planner：限定最多 12 次工具调用、15 分钟默认窗口

Evidence Collector：并行调用独立工具，单次超时与总预算受控

Diagnosis Synthesizer：只根据工具结果形成根因候选

Verifier：检查每条结论是否带证据引用；不足时明确拒答

SSE Presenter：向管理端流式返回步骤、证据和最终报告

安全与审计护栏

独立身份

MCP 使用专用 audience 的短期服务令牌；禁止把用户或下游令牌直接透传。

服务端授权

角色、商家数据范围和查询参数均由 Java 重新校验，不能信任模型提供的 merchantId。

查询约束

指标与索引白名单、最大时间窗、最大结果数、字段脱敏、限流与超时。

完整审计

记录用户问题、模型、工具名、参数摘要、耗时、返回量和诊断引用，不记录密钥。

已确认事实：order-consumer Lag 在 14:05–14:12 从 120 升至 18,430；同一窗口数据库连接池等待 P95 超过 2 秒。

根因候选：订单消费实例连接池耗尽导致处理速率下降（高置信度）。

证据引用：[metric:kafka_lag#时间窗] [metric:hikari_pending#时间窗] [logs:order-service#traceId]

处置建议：人工检查慢 SQL 与连接池配置；Agent 不自动修改配置、不重放消息。

未知项：若证据不足，明确列出还需哪些指标或日志，不编造确定结论。

验收故障样例

  • Kafka 消费者 Lag 激增
  • Outbox 投递任务停滞
  • 库存预占与订单状态不一致
  • 支付回调重复与迟到
  • Sentinel 熔断导致试算失败

首版禁止能力

  • 执行 SQL、Shell 或任意 PromQL
  • 修改 Nacos / Sentinel 配置
  • 自动补偿、退款或消息重放
  • 把原始手机号、地址、令牌送入模型
