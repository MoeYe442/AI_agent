Kafka 事件契约与可靠投递

交付语义为 at-least-once；不追求“消息只到一次”，而是通过 Outbox、Inbox、业务唯一键和状态机让重复到达无副作用。

统一事件信封 EventEnvelope<T>

eventId：UUIDv7，全局去重键

eventType / eventVersion：事件名与整数版本

aggregateType / aggregateId：来源聚合

occurredAt / producer：UTC 时间与服务名

traceId / causationId / correlationId：链路与因果关系

payload：不可变业务快照；金额使用分为单位的 long

Topic 与分区约束

按领域使用版本化 Topic，例如 trade.order-events.v1。

订单内顺序使用 orderId；团内顺序使用 groupId。跨聚合不承诺全局顺序。

消费者必须根据当前数据库状态决定“应用、忽略或补偿”，不能依赖理想到达顺序。

契约只允许向后兼容地新增可选字段；破坏性变化发布 v2 Topic。

生产端：业务与事件同事务
MySQL 本地事务 → Outbox Relay → Kafka

业务表和 event_outbox 同事务提交；Relay 使用 SELECT ... FOR UPDATE SKIP LOCKED 批量领取待投递事件。

Kafka broker 确认后标记 SENT；发送结果不确定时允许再次发送，由消费者幂等吸收。超过重试阈值标记 FAILED 并告警，补偿扫描继续接管。

消费端：幂等、重试与人工重放

1. Inbox 去重

业务事务先插入 event_inbox(eventId, consumer) 唯一键；已存在直接视为成功。

2. 业务幂等

支付单号、reserveToken、结算来源明细等唯一键提供第二道保护。

3. 手动提交

业务事务提交后再 ACK Offset；崩溃窗口造成重投而不是数据丢失。

4. 重试 / DLT

瞬时错误进入指数退避 Topic；不可恢复错误进 DLT，运营台按 eventId 审计重放。

必须监控

  • Outbox 最老待发送时长与失败数
  • 消费者 Lag、重试速率、DLT 堆积
  • 重复事件命中率与状态冲突次数
  • 库存预占与订单状态不一致数量

禁止做法

  • 业务提交后直接“尽力而为”发送 Kafka
  • 把自动提交 Offset 当作处理成功
  • 用同一个 Partition 保证所有业务全局有序
  • 直接修改 DLT 数据而不保留重放审计
