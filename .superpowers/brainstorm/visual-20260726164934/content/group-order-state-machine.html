先支付后成团：交易状态机与补偿边界

MySQL 保存最终业务事实，Redis 负责热点原子预占；每次状态迁移使用版本号 CAS，并在同一事务写入 Outbox。

正常主链路

1. 试算

营销服务返回 promotionSnapshotId、应付金额和过期时间。

2. 原子预占

Redis Lua 校验资格，锁活动 SKU 库存、团名额和参与次数，返回 reserveToken。

3. 待支付

订单落库为 PENDING_PAYMENT，并事务写入 Outbox 与支付截止任务。

4. 已支付待成团

回调幂等后迁移为 PAID_WAITING_GROUP；拼团服务累计已支付成员。

5. 成团确认

达到目标人数：库存预占转实扣，订单变为 CONFIRMED，结算服务生成待结算账单。

PENDING_PAYMENT → PAID_WAITING_GROUP → CONFIRMED
订单聚合状态

PENDING_PAYMENT：库存和名额已预占，等待支付。

PAID_WAITING_GROUP：支付有效，等待达到成团人数。

CONFIRMED：团成功、库存实扣、可进入提货履约。

CLOSING / CLOSED：未支付超时，释放全部预占。

REFUNDING / REFUNDED：已支付但拼团失败，退款后释放资源。

拼团聚合状态

RECRUITING：只统计已支付且回调有效的成员。

SUCCEEDED：CAS 锁定一次，发布 GroupSucceeded。

FAILED：截止时间人数不足，发布 GroupFailed。

同一 groupId 的事件进入同一 Kafka Partition，聚合内有序。

团状态一旦终态不可逆，迟到支付进入退款支线。

四条异常与竞态支线

订单落库失败

reserveToken 未绑定订单；立即执行 Lua 补偿。若进程宕机，由预占 TTL 与库存校正任务兜底。

未支付超时

CAS 将订单迁移到 CLOSING；关闭支付单后释放库存、名额、参与次数，最终 CLOSED。

成团超时

团变为 FAILED；未支付订单关闭，已支付订单进入 REFUNDING，退款成功后释放预占。

支付回调迟到

只有订单仍待支付且团仍招募时才能确认支付；否则记录 LatePaymentDetected 并自动原路退款。

可靠性机制
截止任务不是“假装 Kafka 原生支持延迟消息”

订单/拼团在本地事务写入 deadline_task；Redis ZSet 作为近期任务加速索引，到期后发布 Kafka 超时事件。

数据库定时扫描补发遗漏任务；消费端 Inbox 记录 eventId，业务表唯一键与 version 再做双重幂等。

失败依次进入指数退避重试 Topic、死信 Topic；运营台可查看并执行受审计的人工重放。

状态不变量

  • 有效扣减量 = 预占量 + 已确认量，且永不为负
  • 同一用户同一活动只有一个有效参与记录
  • 一次支付最多确认一个订单，一笔退款最多成功一次
  • 结算只接受 CONFIRMED 且未退款的订单明细

首版明确不做

  • 跨仓调拨与提货点独立库存
  • 真实第三方资金分账
  • 同一活动混用先成团后支付
  • 依赖分布式事务框架锁住整条链路
